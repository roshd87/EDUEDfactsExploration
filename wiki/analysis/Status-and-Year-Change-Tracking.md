# Status and Year Change Tracking

How Ed-Fi and the EDU warehouse should track LEA/school status changes and effective dates, and
convey them to EDFacts and other as-of-date uses. Spike run 2026-10-21: the FS029 business rules
were read against the frozen SY 2026-27 spec, the EDU repos and Airflow were checked for what
survives a refresh, and fifteen candidate designs were generated by independent agents (five with
an open prompt, then ten with one lens each) and ranked. **No approach is chosen.** The decision is
plan §5 E7, taken with E6 at start gate G1.

Related: [[FS029 Directory|FS029]] · [[FS029 Business Rules]] · [[Directory]] (Generate) ·
[[analysis/EDFacts-EdFi-Gap-Analysis|gap analysis]] · `EDFactsOutputPlan.md` §4a (Plan 1), §5.

## 1. What the FS029 rules actually require

Verified in `wiki/edfacts/FS029/FS029 Directory.md` (reporting period, §2.5.1, §6.0, Appendix C)
and `FS029 Business Rules.md`.

1. **The operational status code is a year-over-year transition relative to the prior year's
   EDFacts submission, not a state.** Appendix C Table C-1 validates "Reported Operational Status"
   against "Previously Reported Status". Closed last year admits only Reopened (8); a unit omitted
   last year must be New (3), Added (4) or Future (7); New, Added and Reopened are used for one
   year; Future lasts at most two; reopening is allowed within 10 school years of closing. BRSI
   rules DGO-0011/0012/0022 compare prior-SY submitted values the same way. **DG16/DG531 cannot be
   derived from Ed-Fi alone; it needs what was filed last year.**
2. **DG16N/DG531N + DG571 are one net within-year delta, not a log.** §6.0: one status at SY start
   and at most one new/updated status after it; EDPass accommodates exactly one update. DG571 is
   "the date that the operational status changed". A unit opening after SY start is DG16=7,
   DG16N=3, DG571=open date, NCES id blank.
3. **A corrected SY-start status is not a change.** It overwrites DG16; the N fields stay blank.
4. **Timing is driven by the directory due date.** Known before: in the file. Found after: request a
   correction opportunity from PSC (Partner Support Center, ED's EDFacts/EDPass help desk).
   Operational→nonoperational may wait for next year's directory; nonoperational→operational must be
   reported promptly because no other file can be submitted for the unit until it is.
5. **Reporting period** is October 1 or the closest school day, to coincide with FS052. "SY start"
   itself is undefined in the spec (July 1 vs first instructional day).
6. **Downstream rules read an "Effective" status** = N value if filled, else SY-start value. The
   FS052/FS059 completeness rules (CCD-0029/0031/0047/0049) use the SY-start value.
7. Special situations: no students but staff → Open (1) with FS052 total zero; no staff → Inactive
   (6) and omitted from FS052; Inactive needs a directory row every year.

### Open questions for PSC

- Does "previously reported" in Table C-1 mean the prior year's SY-start value or its effective
  (post-update) value?
- Is "start of the school year" July 1 or the first instructional day?
- §6.0 gives the DG571 limit as 9/30/2026 for LEAs and 9/30/2027 for schools in the SY 2026-27
  spec; the LEA line reads like a carried-over typo.

## 2. What Ed-Fi and EDU provide today (verified 2026-10-21)

- Core Ed-Fi carries one current `operationalStatusDescriptor` per School/LEA, no history, no
  effective date. The Ed-Fi 6.1 default values (Active, Added, Changed, Closed, Future, Inactive,
  New, Reopened) match DG16/DG531 one to one (Active = Open).
- Core School and LEA carry an `indicators[]` collection with dated `periods[]`;
  `base_ef3__schools` / `base_ef3__local_education_agencies` already expose it as `v_indicators`.
  Nothing flattens it. Ed-Fi ships no default IndicatorDescriptor values.
- `stg_ef3__schools` / `stg_ef3__local_education_agencies` dedupe within api_year by
  `last_modified_timestamp`, then across api_years keeping the latest year, so
  `dim_school.operational_status` is today's value and a prior-year rerun reports today's status.
  Each api_year ODS is effectively an annual copy of the org.
- **Raw landing tables are not durable history.** `ObjectStorageToDatabaseOperator` runs
  `DELETE FROM` on `full_refresh`, and `schedule_interval_full_refresh` exists. Pull JSONL files land
  in object storage first; retention is deployment-specific. Airflow also lands `_deletes` and
  (Ed-Fi 6+) `_key_changes`.
- dbt snapshots are an existing pattern in a partner repo (`stadium_south_carolina`,
  `msr_student_adm_snapshot`, `strategy='check'`).

## 3. Round 1: five open-prompt designs

Same prompt, no lens. Consumption layer was unanimous: an SCD-2 fact (org × status_type ×
valid_from, exclusive valid_to), a `status_as_of` macro, `dim_school` untouched, declared beats
observed, an overrides seed, DG16 = as-of SY start, DG16N = last change in (SY start, cutoff],
DG571 = its date, "operational on the count date" = codes 1/3/4/5/8.

| Rank | Design | Declared source | Observed source | Distinctive |
|---|---|---|---|---|
| 1 | A | core `indicators[].periods[]` | dbt snapshots in edu_wh | never submits a pull date as DG571 (test fails) |
| 2 | C | core indicators | rebuilt from raw | `edfacts_submitted_directory` snapshot; derives New/Reopened/Changed from last year's filing |
| 3 | B | narrow Ed-Fi extension date field | append-only hashed versions model in edu_edfi_source | labelled date ladder; bitemporal `known_at` |
| 4 | D | MetaEd extension entity | rebuilt from raw | observed changes feed a review sheet → overrides |
| 5 | E | core indicators | rebuilt from raw | Table C-1 as a dbt test |

Lessons: three of five assumed raw is durable (it is not). Only C handled that DG16 is a
transition relative to the prior filing. Round 2 was briefed with both facts.

## 4. Round 2: ten designs, one lens each

Scores 1–5 per criterion; correctness against the FS029 rules is the tiebreaker.

| Rank | Solution (lens) | Correct | Durable | No ODS change | Cost | Reuse | Total |
|---|---|---|---|---|---|---|---|
| 1 | 2. EDPass filing ledger | 5 | 5 | 5 | 5 | 2 | 22 |
| 2 | 9. Generic dated-attribute framework | 4 | 5 | 5 | 3 | 5 | 22 |
| 3 | 10. Workflow-first status desk | 5 | 5 | 4 | 4 | 2 | 20 |
| 4 | 8. Full composite with review queue | 5 | 5 | 4 | 2 | 4 | 20 |
| 5 | 7. Per-school-year org dimensions | 4 | 4 | 5 | 4 | 3 | 20 |
| 6 | 4. Object-storage version capture | 4 | 5 | 4 | 2 | 4 | 19 |
| 7 | 1. No-history minimum | 4 | 4 | 5 | 5 | 1 | 19 |
| 8 | 5. Inferred lifecycle events | 3 | 4 | 5 | 3 | 4 | 19 |
| 9 | 3. SEA directory via side-door | 4 | 5 | 3 | 3 | 3 | 18 |
| 10 | 6. Typed Ed-Fi extension | 5 | 4 | 1 | 3 | 2 | 15 |

**2. EDPass filing ledger.** Every accepted FS029 record parsed verbatim into a git seed
(`edfacts_filed_directory`: school_year × org_level × unit × submission_seq, with
`record_text`, DG16/DG16N/DG571, NCES id, `submission_kind`, `file_sha256`, `accepted_on`), plus a
declarations seed (`edfacts_status_declarations`, one row per unit per year: new_status,
effective_date, kind ∈ change/correction/added/changed_agency), Table C-1 as a seed, a
reconciliation model proposing DG16/DG16N/DG571 with an `action` column
(include / request_correction_opportunity / optional_or_defer), and a parser task for backfill
from the SEA's FS029 archive or NCES CCD files. Ed-Fi is observed per api_year from base models.
Nothing changes in edu_edfi_source or edu_wh. Weak on as-of dates outside EDFacts.

**9. Generic dated-attribute framework.** A var registry (`edu:dated_attributes`) and three macros
(`as_of`, `change_between`, `dated_attribute_union`). Attributes Ed-Fi already dates (indicator
periods, program participation statuses, SEOA characteristic periods, staff assignment dates) are
read in place; undated attributes on small resources get one dbt snapshot per entity keyed by
`k || api_year` so annual ODS copies become free year-end history; the prior filing is registered as
a dated attribute fed by a `freeze_submission` run-operation. Student-scale entries are never
snapshotted. Heavier than FS029 alone needs; pays off at FS129/FS141/FS059.

**10. Workflow-first status desk.** A named SEA directory steward keeps a git-reviewed ledger
(`edfacts_org_status_ledger`: school_year × org × status_type × entry ∈ {sy_start, change}, with
decision, evidence_ref, decided_by, psc_ticket), backed by the filed-directory seed and a daily
proposals model (descriptor drift, missing Inactive rows, students at nonoperational units, C-1
violations, missing PSC tickets). Roles, triggers and six annual checkpoints are specified. Catches
intent (change vs correction, New vs Added) that no automated history can. Depends on a staffed
steward.

**8. Full composite.** Precedence override > indicator > prior_submission > observed > scalar;
core indicator periods flattened; `snp_org_status` dbt snapshot; an acceptance ledger written only
by `edfacts_record_acceptance` (hash-verified, idempotent); overrides filled through a blocking
review queue (`rpt_org_status_review`: conflict / undated_change / correction_candidate /
new_vs_added); twenty tests including C-1, C-2, Future ≤ 2 years, Reopened within 10 years. Most
complete; blocking reviews can stall a deadline.

**7. Per-school-year org dimensions.** `bld_ef3__schools_by_year` / `leas_by_year` from base
models without the cross-year dedupe (incremental, `full_refresh=false`), `dim_school_by_year`
and `dim_lea_by_year` pinning every annual attribute, an append-only `fct_org_year_reported`
frozen at each final submission, and C-1 as a self-join on year−1. Derives Changed (5) from the
LEA key, which no other design does. No observed source for DG571 at all.

**4. Object-storage version capture.** An Airflow operator copies each pull's school/LEA JSONL
(plus `_deletes`, `_key_changes`) to a write-once `history/` prefix with a manifest; an external
table feeds `stg_ef3__org_versions` and `fct_org_status_periods` with `known_as_of` replay. The
most durable observed history; needs an upstream Airflow release and per-deployment
infrastructure.

**1. No-history minimum.** Current `dim_*` status + the prior filed seed + a one-row-per-unit-year
changes seed + C-1 seed; the export writes next year's prior-filing seed itself. Lowest cost;
reuse 1.

**5. Inferred lifecycle events.** Diff consecutive api_year copies and date events from calendars,
enrollment, staff assignments and deletes, each with a confidence grade
(`fct_org_lifecycle_event`). Can infer New, Future, Changed (school), Closed, Inactive, Open;
cannot infer Added, LEA boundary change, correction, or merge. Closure dates approximate; late
calendars make live schools look Future.

**3. SEA directory via side-door.** The SEA's master directory exports dated events through an
earthmover bundle with a fixed contract (`org_status_events.csv`: org_level, state_org_id,
status_type, status_value, event_type, effective_date, successor_state_org_id, source_event_id)
into an append-only side-door table; Ed-Fi is reconciled against it. Assumes a dated directory
exists; nothing for LEA-run deployments.

**6. Typed Ed-Fi extension.** MetaEd `Common DirectoryStatus` keyed by SchoolYear with
StartOfYear / Updated / PriorYearReported OperationalStatus, `UpdatedStatusEffectiveDate` and a
correction flag, as a collection on School and LEA mirroring core `accountabilities[]`. Cleanest
model and a candidate for an Ed-Fi tracker proposal; requires an extension per partner, which plan
§6 rules out.

### Overlap

- Ranks 1, 3 and 7 are one family (filing ledger + declarations seed, no observed history);
  rank 1 is the best specified.
- Ranks 2, 5 and 8 all read the per-api_year ODS copies without the cross-year dedupe. That alone
  fixes prior-year reruns and belongs in any choice.
- Ranks 2, 4 and 8 are the three durable observed-capture options (registry snapshots, object
  storage files, plain dbt snapshots). Rank 4 reproduces round 1's composite; rank 10 is round 1's
  D keyed by school year.

## 5. Settled regardless of choice

Every one of the fifteen designs converged on these; treat them as requirements:

1. **The prior EDFacts filing is stored as a first-class fact** (parsed FS029 records or the EDPass
   directory download), because DG16 is validated against it.
2. **The N fields are a single net change** from SY start to the latest status before the cutoff;
   corrections rewrite DG16 and never populate N.
3. **A pull or last-modified timestamp is never submitted as DG571.** Observed changes are
   evidence for review, not an effective date.
4. **`dim_school` / `dim_lea` stay current-state.** History lives beside them, never in them.
5. **Prior-year reruns must read that year's org state**, not today's. The cheapest fix is a
   by-year build over the base models.

## 6. Recommendation (not a decision)

Adopt solution 2 (filing ledger + declarations) inside Plan 1's scope, since every other design
assumes its ledger anyway, and add solution 7's by-year build models for prior-year reruns at the
same time. Defer solution 9's registry and snapshots until FS129, FS141 or FS002 need an as-of
date that is not year-grained. Revisit solution 6 only if a partner already runs extensions and
wants the yearly status in the ODS for other consumers.

What this changes in Plan 1 (`EDFactsOutputPlan.md` §4a): the two "manual" items for dated
operational-status changes and the "opened after the count date" build gap are absorbed by the
ledger and declarations seeds; `edfacts_directory_overrides` shrinks to authorizer ids,
reconstituted status and prior ids.
